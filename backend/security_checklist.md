# RWA Protocol Security Checklist

This checklist covers all the critical security vectors we have patched and discussed. You can use this to systematically verify your platform's security.

## 1. API Security & Authentication (Zero-Trust)
- [x] **Missing JWT Token:** Send a GraphQL request (e.g., `getRefundSignature`) with no `Authorization` header.
  - *Expected:* Request is instantly rejected with `UNAUTHENTICATED`.
- [x] **Forged/Modified JWT Token:** Take a valid JWT, change one character in the payload (like the wallet address), and send a request.
  - *Expected:* Request is rejected because the cryptographic signature of the JWT becomes invalid.
- [] **Wallet Address Spoofing (CRITICAL):** Attempt to send a GraphQL request requesting a refund or mint for a transaction ID that belongs to a *different* user.
  - *Expected:* The backend must fetch the user's wallet address directly from the database (linked to the validated Privy JWT) and refuse to process transactions belonging to other users.

## 2. Signature & Replay Attacks
- [x] **Race Condition / TOCTOU (Time-of-Check to Time-of-Use):** Run `test_replay.js` to fire 5 identical signature requests at the exact same millisecond.
  - *Expected:* Redis `setNX` lock blocks 4 of them. Only 1 valid signature is returned.
- [x] **Smart Contract Signature Replay:** Take a valid signature generated by the backend and successfully use it to call `cancelMint` (or `depositForMint`) on the smart contract. Then, try to call the exact same function again with the exact same signature.
  - *Expected:* The smart contract reverts the transaction because the signature is marked as used in the `s_usedSignatures` mapping.
- [x] **Cross-Function Signature Replay:** Take a valid signature intended for `cancelMint` and try to use it as the parameter for `redeem` or `claimMint`.
  - *Expected:* The smart contract reverts. The `keccak256` hash in the contract expects a specific string (e.g., `"cancelMint"`), so signatures cannot be recycled across different functions.

## 3. Smart Contract Logic & Financial Math
- [x] **Oracle Access Control:** Connect your frontend wallet and attempt to call `mint()` or `redeem()` directly on the smart contract (bypassing the backend).
  - *Expected:* The contract reverts with an `OwnableUnauthorizedAccount` or similar error, because only the backend Oracle address has the power to mint/burn.
- [ ] **Decimal Truncation Precision:** Create an order that results in a fractional dTSLA amount with more than 18 decimal places.
  - *Expected:* The backend string-truncation logic (`safeQtyStr.split('.')[1].substring(0, 18)`) correctly truncates the dust without crashing or throwing BigInt parsing errors.
- [x] **Insufficient USDC Balance:** Try to call `depositForMint` with 5 USDC when your wallet only has 2 USDC (or hasn't granted enough ERC-20 allowance to the contract).
  - *Expected:* The ERC-20 `transferFrom` fails and the contract reverts.

## 4. Webhook & Database Integrity
- [ ] **Alpaca Webhook Spoofing:** Use an API testing tool (like Postman) to send a fake HTTP POST request to your Alpaca Webhook endpoint claiming an order was "filled".
  - *Expected:* The backend rejects the request because the SVIX/Webhook signature header doesn't match your secret key.
- [x] **Order Cancellation Desync:** Cancel an order directly in the Alpaca Dashboard while the backend is running.
  - *Expected:* The `indexer.js` WebSocket immediately catches the cancellation and securely updates the database status to `CANCELED_BY_ADMIN` or `FAILED`, allowing the user to claim a refund signature.

## 5. Advanced Edge Cases & Exploit Vectors
- [ ] **Signature Expiry (Time-Based):** Generate a valid signature from the backend (e.g., for `cancelMint`), wait exactly 6 minutes, and then try to submit it to the smart contract.
  - *Expected:* The smart contract reverts with a timeout/expired error because `block.timestamp` is too far past the signature's embedded timestamp.
- [ ] **Dust / Zero-Value Redemptions:** Request a `redeem` for an infinitesimally small amount of dTSLA (e.g., `0.000000000000000001` dTSLA) that mathematically rounds to `$0.00` USDC.
  - *Expected:* The backend safely rejects the transaction or handles the 0 amount without causing a division-by-zero crash or underflow.
- [ ] **Market Closed / Upstream Failure:** Trigger a `MINT` when the US stock market is explicitly closed (weekend/holiday) or when Alpaca API rate limits are intentionally exceeded.
  - *Expected:* The backend catches the Alpaca API failure, gracefully marks the transaction as `FAILED` in the database, and allows the user to cleanly pull a refund signature.
- [ ] **GraphQL Payload Injection (SQLi):** Send a GraphQL request passing a malicious string into `transactionHash` (e.g., `' OR 1=1; --`).
  - *Expected:* The backend's parameterized PostgreSQL queries (`$1`) neutralize the payload, returning a standard "Transaction not found" error rather than dumping data.
- [ ] **Indexer Idempotency (Chain Reorg Simulation):** Manually force `indexer.js` to process the exact same `DepositForMint` blockchain event log twice in a row.
  - *Expected:* The indexer detects the `blockchain_tx` hash is already in the database and ignores the duplicate, preventing 2 Alpaca orders from being placed for 1 payment.
